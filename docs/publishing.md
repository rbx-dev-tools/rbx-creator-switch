# Publishing

How a release reaches the Chrome Web Store. The first listing is made by
hand in the developer console; every tag after that is uploaded and
published by `.github/workflows/release.yml`.

## The listing

Copy for the store page. Keep it in step with the README: the store text is
what a reviewer at Google reads, and a permission or a host that appears in
one and not the other is the kind of mismatch that gets a review bounced.

**Name**: rbx-creator-switch

**Summary** (132 characters max):

> Pick a Roblox account, a creator and an experience in one popup, with
> pictures, instead of walking the Creator Hub menus.

**Description**:

> The Creator Hub spreads one choice over three places: the profile menu for
> the account, the menu on the left for the creator, the grid for the
> experience. This popup puts the three side by side, each row with its
> picture, because a list of thirty names makes you read where a list of
> icons lets you recognise.
>
> Type a name in the search field and press Enter to land on an experience
> whichever creator or account it sits under. The popup switches account
> for you if it has to, and says so before you pick.
>
> It only ever talks to roblox.com. No telemetry, no analytics, no remote
> code. It never reads your cookies: requests are sent by the browser with
> your session attached, the way the Creator Hub's own requests are. What
> it stores is a cache of your creator and experience lists, on your
> machine.
>
> Not affiliated with Roblox. It uses endpoints Roblox does not document,
> which can change without notice; when they do, this extension stops
> working until it is updated, and the source at
> https://github.com/rbx-dev-tools/rbx-creator-switch says exactly which
> endpoints and what breakage looks like.

**Category**: Developer Tools. **Language**: English.

**Assets**: `icons/icon-128.png` for the store icon, and the three pictures
in `docs/screenshots/store-*.png` (1280x800, regenerated by
`npm run screenshots`).

**Visibility**: Unlisted to start with. The link installs, search does not
find it. Public can come later without resubmitting.

## The privacy tab

Google asks for a justification per permission. These are the true ones.

- **`scripting`**: injects `src/agent.js` into an open roblox.com tab to call
  Roblox's own APIs from that origin, which is the only origin the session
  cookies and the account switcher state are available to. Nothing is
  injected into any other site.
- **`storage`**: keeps a per-account cache of the creator and experience
  lists, and the theme preference, in `chrome.storage.local`. Nothing leaves
  the machine.
- **Host permission `https://*.roblox.com/*`**: to find a roblox.com tab,
  inject into it, and let that tab call `apis.roblox.com` and
  `thumbnails.roblox.com`. No other host is contacted.
- **Remote code**: none. Every line that runs ships in the package.
- **Data use**: the extension does not collect, transmit or sell any user
  data. It reads `localStorage.RBXASBlob` on `www.roblox.com`, the account
  switcher record, and sends it only to the Roblox endpoint the site itself
  sends it to.
- **Single purpose**: navigating to a creator's experience in the Creator
  Hub.

## The first upload, by hand

1. Build the package the way the release workflow does, from a clean tree:

   ```bash
   mkdir -p dist && cp -r manifest.json src icons LICENSE dist/ && (cd dist && zip -qr ../rbx-creator-switch.zip .) && rm -r dist
   ```

2. In <https://chrome.google.com/webstore/devconsole>, **New item**, upload
   the zip, fill the listing and privacy tabs from above, set visibility,
   submit for review. Review takes hours to a few days for a first version.
3. Note the **item ID** shown in the console (32 lowercase letters). It is
   the `CWS_EXTENSION_ID` below, and it never changes.

## Automating the rest

Done once, with the same Google account as the store.

1. **Google Cloud**: <https://console.cloud.google.com>, create a project
   (any name), then **APIs & Services > Library**, enable **Chrome Web Store
   API**.
2. **OAuth consent screen**: External, app name anything, your email for
   both contacts, save. Under **Audience**, add your own address as a test
   user (the app never needs to be verified for a single user).
3. **Credentials > Create credentials > OAuth client ID**, type **Desktop
   app**. Keep the client ID and client secret that appear.
4. **Refresh token**: open in a browser, with your client ID in place:

   ```
   https://accounts.google.com/o/oauth2/auth?response_type=code&scope=https://www.googleapis.com/auth/chromewebstore&client_id=CLIENT_ID&redirect_uri=urn:ietf:wg:oauth:2.0:oob&access_type=offline&prompt=consent
   ```

   Approve, copy the code shown, then exchange it:

   ```bash
   curl -X POST https://oauth2.googleapis.com/token -d client_id=CLIENT_ID -d client_secret=CLIENT_SECRET -d code=CODE -d grant_type=authorization_code -d redirect_uri=urn:ietf:wg:oauth:2.0:oob
   ```

   The answer carries `refresh_token`. It does not expire as long as the
   OAuth app stays in testing and is used at least every six months, which a
   release cadence satisfies; if it ever stops working, repeat this step.

5. **GitHub**, repository **Settings > Secrets and variables > Actions**:
   - Secrets: `CWS_CLIENT_ID`, `CWS_CLIENT_SECRET`, `CWS_REFRESH_TOKEN`.
   - Variable: `CWS_EXTENSION_ID`.

   The publish step in `release.yml` is skipped until the variable exists,
   so a release can be cut before any of this is done.

## A release, after that

1. Bump `version` in `manifest.json`, move the `[Unreleased]` section of
   `CHANGELOG.md` under the new version, commit.
2. `git tag v0.2.0 && git push --tags`.
3. The workflow checks the tag against the manifest, builds the zip,
   attaches it to a GitHub release with its checksum, uploads it to the
   store and publishes. Google reviews updates too, usually within the
   hour; the console shows the state.

None of the values above ever belong in the repository, a commit message or
an issue. The secrets go into GitHub's secret store and nowhere else.
